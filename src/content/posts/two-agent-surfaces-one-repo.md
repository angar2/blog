## 한 도구의 설정 폴더에 다른 도구를 얹으면 표면이 종속된다

클로드코드에 맞춰 둔 자동화에 코덱스를 두 번째 도구로 붙일 때, 처음에는 코덱스가 클로드 폴더의 파일을 빌려 쓰게 연결했다. 두 도구가 같은 자동화를 쓰더라도 한쪽의 설정 폴더가 다른 쪽의 본체가 되면, 추가된 도구는 독립된 표면이 아니라 기존 표면에 얹힌 부속물처럼 남는다.

여기서 표면은 같은 자동화를 사용하는 각 AI 코딩 도구의 설정·실행 접점이다. 러너는 공용 본체를 각 도구의 실행 방식에 맞게 연결하는 얇은 실행 파일 또는 설정이다. 내가 다시 잡은 기준은 단순했다. 실행되는 본체는 도구 중립 위치에 두고, 각 도구 폴더에는 그 본체를 부르는 러너만 둔다.

공통 문서도 복제하지 않았다. 한쪽에 원본을 두고 다른 쪽은 임포트 한 줄로 참조하게 했다. 같은 내용을 두 파일에 복제하면 수정 뒤 어느 쪽이 최신인지 다시 관리해야 하고, 두 표면은 처음부터 다른 규칙을 보게 된다.

세 번째 도구가 들어와도 본체를 건드리지 않고 러너만 추가할 수 있는가를 구조의 판정 기준으로 삼았다. 아직 세 번째 도구를 실제로 연결하지는 않았으므로, 이 기준은 재편 방향을 점검하는 질문이지 검증된 확장성의 결과는 아니다.

## 훅과 세션은 도구마다 다른 조건을 가진다

공용 본체를 분리해도 각 도구의 설정과 실행 조건까지 같아지지는 않는다. 코덱스 쪽에서는 설정 파일에 훅을 등록해도 신뢰 승인을 받기 전에는 아무 오류 없이 실행되지 않았다. 명령 훅마다 현재 파일 해시를 신뢰 처리해야 했고, 파일을 조금만 고쳐도 다시 미승인 상태가 됐다. 훅은 새 세션부터 적용되므로 이미 열려 있던 대화에는 소급되지 않았다.

세션 시작 때 주입하는 내용도 약 10KB에서 잘렸다. 47.8KB를 넣었을 때 카탈로그 파일은 통째로 빠지고 나머지는 임시 파일로 밀려났다. 세션 종료 이벤트는 대화를 보관·삭제하거나 30분 방치했을 때만 실제로 발생해, 수확 지점을 세션 종료가 아니라 세션 시작으로 옮겼다. 세션을 열자마자 닫으면 기록 파일 자체가 만들어지지 않아 검증할 수도 없었다.

이 차이는 이름이 같다고 역할도 같을 것이라고 가정하면 더 쉽게 놓친다. 두 도구에 모두 `rules`라는 폴더가 있었지만, 한쪽은 에이전트 행동 규칙 문서를 두는 곳이었고 다른 쪽은 셸 명령을 `allow`·`prompt`·`forbidden`으로 나누는 권한 정책 폴더였다. 전역 지침을 읽는 방식도 달랐다. 한쪽은 전역 지침 파일과 규칙 폴더의 직속 파일을 상시 읽었고, 다른 쪽은 지침 파일 하나만 자동으로 읽었다. 후자의 지침 파일은 필요한 규칙을 찾아 읽게 하는 안내판 역할을 맡았다.

공용 본체는 동작을 한곳에 모으는 장치일 뿐이다. 훅 승인, 주입 한도, 이벤트가 실제로 발생하는 조건처럼 도구가 가진 제약은 러너를 만들기 전에 따로 확인해야 한다.

## 기록을 처리하기 전에는 출처와 크기를 먼저 정규화한다

도구 표면을 나누는 일은 실행 파일의 위치만 정하는 일이 아니었다. 대화 기록과 큐 데이터가 어느 표면에서 온 것인지, 그대로 처리할 수 있는 크기인지도 먼저 확인해야 했다.

대화 기록 한 줄에 이미지가 base64로 통째로 들어가면서 511줄짜리 기록이 118MB가 된 적이 있다. base64는 이미지 같은 이진 데이터를 텍스트로 기록하는 방식이다. 사람 발화와 답변만 추출하는 리더를 거치자 같은 기록은 21KB가 됐다. 원본을 그대로 자동화에 넣는 대신, 필요한 대화만 읽는 경계를 둔 이유다.

큐 레코드도 판정보다 출처 정규화가 먼저였다. 14줄 가운데 9줄에는 어느 표면에서 왔는지 나타내는 필드가 없었고, 그중 하나는 자동화 자체의 실행 로그였다. 이 상태로 처리하면 기계 실행 기록이 사람 작업으로 섞여 지식에 들어갈 수 있다.

경계는 리포 안에서만 끊기지 않았다. 스크립트를 옮기며 옛 경로를 지웠을 때 리포 밖의 크론이 그 삭제된 경로를 계속 호출하고 있었다. 코덱스 데스크톱은 대화마다 날짜와 대화 식별자로 된 임시 폴더를 만들었고, 그 폴더명이 프로젝트 이름 자리에 들어가 잡담 한 건이 가짜 프로젝트를 만들 뻔한 사례도 세 번 있었다. 공용 본체와 러너를 분리한 뒤에도, 입력 데이터가 무엇을 뜻하는지와 어디에서 호출되는지는 별도의 경계로 남는다.

## 아직 확인하지 못한 두 경계

재편 뒤에는 코덱스 세션이 정상적으로 처리되는 것까지 확인했다. 배선 대상인 코덱스에게 교차 검토를 시켰을 때 훅 신뢰 미승인도 발견됐다. 다만 세 번째 표면을 실제로 연결해 러너만 설치하면 되는지는 아직 실증하지 않았다.

훅 파일을 수정할 때마다 다시 필요한 신뢰 승인이 장기 운용에서 어느 정도 마찰을 만드는지도 관측 기간이 짧다. 공용 동작을 하나로 모으는 일과 각 도구의 실행 조건을 확인하는 일은 서로 대체되지 않는다. 여러 도구를 같은 자동화에 붙일 때는 설정 파일을 합치기보다, 공용 본체와 도구별 러너가 어디에서 갈리는지부터 확인해야 한다.
